# CLAUDE.md

Guidance for every Claude Code session in this repo. The full product brief lives in `docs/brief.md`; read it before any substantial change.

Next.js notes (managed by Next.js itself): @AGENTS.md

## How to work

- Work in small, verified units. Each unit is one coherent change that typechecks and builds. Commit after every unit with a clear message. Never leave the repo in a state that does not build.
- Before committing, run `npm run verify`: typecheck, lint, copy rules, unit tests, production build, and a check that every Tailwind class used actually exists (Tailwind is limited to the tokens, so a missing token fails silently otherwise).
- Collect questions instead of scattering them through prose. Present each with the choices and a recommended answer. Proceed on the recommendation for anything low-risk while waiting. Stop and ask before any decision that is hard to reverse.
- Do not invent copy, numbers, names, or claims about the product beyond what `docs/brief.md` gives. Where placeholder text is needed, make it obviously placeholder and list it in `PLACEHOLDERS.md`.
- Report in plain language: what changed and what the owner can now do, not how the internals are wired.
- Report at the end of each build phase: what works, what is needed from the owner, and the current placeholder list.
- When brand assets or mockups arrive, applying them takes priority over the current phase.

## Sessions in the Replit shell

The owner runs Claude Code in the Replit shell (started with `./cc`) and watches changes land in a browser tab. You are in Replit when `REPLIT_DEV_DOMAIN` is set. There, before anything else in every session:

1. Run `node scripts/dev-server.mjs`. It checks the site's dev server (running, hot reloading, reachable through the dev URL), prints the dev URL, and exits 1 when something needs attention. Do what its messages say:
   - **DOWN:** run `node scripts/dev-server.mjs serve` as a background task (`run_in_background`), wait for `[serve] up`, then check again. Only ever run one `serve`; the server it starts stops when the session ends.
   - **STARTING:** the server is starting or recompiling. Check again in about 10 seconds.
   - **NO HOT RELOAD, PORT TAKEN, dev URL FAILS, or MISROUTED:** something else holds the port or the dev URL, usually the Run button or a workflow left from an earlier setup. Claude Code cannot stop those, so ask the owner to stop them in Replit, then check again.
2. Give the owner the dev URL and say whether the site is live there. The admin (`/admin`) signs in only at that address in its own tab, not in Replit's embedded preview.
3. If the site shows errors, deal with them or report them before other work. The dev server writes its errors to `.next/dev/logs/next-development.log`.

While `serve` runs, the owner should not press Run: Next.js allows one dev server per folder, so that second copy just stops. Code changes hot reload, and the dev server applies new migrations by itself when a pull brings them (`src/server/dev-migrations.ts`). It does the same the moment you add one: a new custom migration waits while it is still empty, then applies as soon as its SQL is saved, so save the whole SQL in one step. After pulling changes that touch `package.json`, `next.config.ts`, or environment variables, restart the dev server (stop the `serve` task and start it again, or ask the owner to stop and press Run) so packages install and settings reload. Replit Agent must not restructure this project; `replit.md` tells it so.

## Design system rules

- Every color, font, radius, shadow, spacing, and motion value lives in `src/theme/tokens.ts`. Components reference tokens only (Tailwind utilities generated from tokens, or CSS variables). No hex values, font stacks, or magic shadows in components.
- Brand assets live in `public/brand/` and are mapped in `public/brand/manifest.json`. Components render marks with `<BrandMark name="...">` (via `src/brand`), never by file path, so swapping a file never touches a component. Never edit the supplied artwork files. Do not draw logos; artwork still pending uses a clearly marked placeholder.
- Oppie's look and motion follow `docs/brand/oppie-8e-handoff.md`, the owner's handoff: five rounded pills, one per module in brand order, a jewel tone at the top fading into graphite. `<OppieMark>` (`src/components/brand/oppie-mark.tsx`) draws them with colors and timing from tokens; the supplied SVGs are in `public/brand/oppie/`. It has two states. At `rest` it stands still. While `thinking` (forming or streaming an answer) each pill turns over like a coin, rippling left to right; when thinking ends, each finishes its turn and settles facing forward. Change `state` on the same element rather than swapping marks, and never use the flip as a loading spinner for anything else. Three exceptions, at the owner's request: the hero console's mark keeps turning while its demo runs (it holds still when the demo is paused), `greet` turns a mark over once when it first scrolls into view (the large mark in the Oppie section, and the one in the middle of the platform section's network), and `flicker` lets that network mark dim and brighten slowly, like a pilot light, while it is on screen (the mark is a button that pauses it, since anything that auto-cycles needs a pause control). Under 24px use `still`; from about 120px up use `large`, the owner's finer highlight and edge for big marks (tokens `brand.oppie.large`). When several marks are visible at once, only the active one moves; `paused` freezes one where it is. The static files in `public/brand/oppie/` are for email, print, and share images.
- Brand colors come from the supplied artwork: the wordmark's metal gradient (`text-metal`), the five jewels (`jewel-*` utilities), and the favicon ground for the dark canvas. The jewels read left to right as Build, Studios, Playbook, University, Compass; that is also the brand order for showing the modules.
- In hand-written CSS, reference the per-theme `--o-*` variables, not Tailwind's `--color-*` variables, so nested `data-theme` regions resolve correctly.
- `cn()` only joins class names; it does not resolve conflicts. Never pass a `className` that fights a component's own classes (display, padding, size, colors): which one wins depends on stylesheet order, not on the order you wrote them. Add a variant or size to the component instead, or wrap it.
- Next.js replaces a layout's `openGraph` object wholesale when a page sets its own, so public pages build theirs with `openGraph()` from `src/content/metadata.ts`.
- Form actions return the submitted `values` and forms render `defaultValue` from `state.values ?? saved`, because React resets uncontrolled fields after every form action.
- Editable copy lives in `src/content/registry.ts` (fields plus seed copy per section). Pages read it with `getPage()` from `src/content/store.ts`; never hardcode public copy in components.
- Headline fields (`headline: true` in `src/content/fields.ts`) take line breaks and emphasis: in the admin's small box Enter starts a new line, and words between asterisks are set in italics, in the headline's own metal. Render every headline with `renderHeadline()` from `src/lib/headline.tsx`, and use `plainHeadline()` wherever a headline is plain text, such as a page title or the share image.
- Browser code (`'use client'` and anything it imports) must not import values from `src/content/registry.ts`: it carries every section's validation and seed copy, which would ship to every visitor. Put small values the browser needs in `src/content/constants.ts`; type-only imports are fine.
- For narrower page columns use `<Container size="3xl">` and similar, never a `max-w-*` class on Container.
- A brand mark at the top of a page gets `priority` on `<BrandMark>`, which preloads it: on phones the header wordmark is the largest thing painted first.
- Use the full marks (`opero`, `operovia`): they carry the glossy jewels and the brushed-metal wordmark. The small exports (`-small`, `-tiny`, the xh16/xh22 and flat files) have flat jewels and a flat wordmark; keep them for tiny sizes only. CSS jewels (`jewel-*`) are built layer for layer from the full mark's jewels (`jewelGradient` in `src/theme/css.ts`), so they match the logo at any size.
- Anything that changes what the public site shows must go through `changeContent()` (`src/server/content-version.ts`) so every server instance refreshes.
- `npm run typecheck` regenerates route types first; after adding a route, run it before trusting TypeScript errors about `PageProps`.
- The site's face is Plus Jakarta Sans. The one other face, Mr Dafoe (`font-signature`, `src/theme/fonts.ts`, not preloaded), is for the founder's handwritten signature at the foot of his letter (`src/components/site/founder/letter.tsx`) and nothing else.
- Light and dark themes are both wired. The public site defaults to dark.
- Headline type must feel open and generous: loosen line height and tracking, never condense. Body type must be comfortable at length.
- `text-metal` gives the tails of g, j, p, q, and y room below the last line (the metal is painted only inside the element's box) and takes it back with a negative bottom margin. So never set a bottom margin on metal text, and never space it with `space-y-*` on its parent (that works by bottom margins): space it with the next element's top margin or a flex or grid gap.
- Motion uses transform and opacity only, holds 60fps, and fully respects `prefers-reduced-motion`. Anything that auto-cycles needs a pause control. One exception, from Claude Design's handoff at the owner's request: the figures in the hero and in the proof section, the words the problem section's closing line names (its `closingGold` field, "one platform") and the words the platform section's headline names (its `headlineGold` field, "connected", through `renderHeadline`'s second argument), are gold with a soft light sweeping across them (`.gold-shimmer` in `globals.css`, colors `brand.shimmerGold`, timing `motion.shimmer` in `tokens.ts`), a moving text gradient that repeats every four seconds with no pause control; under reduced motion they stand still in plain gold.
- The front door (`/welcome`, `src/components/door`) never redirects on the server: its cookie-setting action re-renders the page, so a redirect thrown there would navigate out from under the dissolving door; returning guests are handled on the door itself. A link can fill in the door's address (`/welcome?email=`, `DOOR_EMAIL_PARAM`, checked by `doorPrefill`), and a press sooner than `DOOR_MIN_FILL_MS` after the page opened is held by the door while its light runs, never refused; the action's own check stays. Never add a `loading.tsx` under `(site)`: the door relies on the home page committing whole, in one go, under the veil. The veil lives in the root layout and hands off to the hero through `data-door-arrival` on `<html>`, which only `door-arrival.tsx` removes.
- A guest's personal link (`/welcome?invite=`, `DOOR_INVITE_PARAM`) carries a secret of 32 random bytes made for that guest (`link_token` on the guest list), so the door may say who it is for: it fills in their address and, with a welcome name (`greeting`, set on the Guests page), greets them by it (the door's `personalTitle`; `{name}` in the copy, filled by `fillName()` in `src/lib/greeting.ts`) and rolls out the red carpet (`<Carpet>`, `src/components/site/carpet.tsx`: the crimson jewel, timing in `motion.carpet`); the home page greets them above the headline (the hero's `guestGreeting`). Every other link, and a secret that names nobody, gets the plain door, so the door never tells who is invited. An admin opening a personal link sees it as the guest will and lands on `/?invite=` with their greeting: `enterDoor` never gives an admin a guest key or records the guest's visit. Only misses count against an address's rate limit, so a forwarded invitation lets everyone holding it in.
- A company on the guest list (`guest_domains`, the Companies card on the Guests page; the domain helpers in `src/lib/guest-domains.ts`, which refuse email services anyone can sign up for) lets in anyone with an address at its domain, but never on the typed address alone: the door's action emails them a one-time link (`/welcome?confirm=`, `DOOR_CONFIRM_PARAM`; 32 random bytes, only its SHA-256 kept in `guest_confirmations`, spent once, within `CONFIRM_TTL_HOURS`) and answers `DOOR_SENT`, with or without JavaScript, but only once the email service has taken the email: otherwise it answers `trouble`, and on the published site without `RESEND_API_KEY` nothing counts as sent. Every email the service refuses is kept for the Site health card on the Dashboard (`emailHealth()` in `src/server/health.ts`, recorded by `src/server/email/send.ts`). Opening the link only fills in the address and carries the secret back in a hidden field (opening it changes nothing, so mail scanners that open links spend nothing); entering there spends it and makes the person a guest of their own, with `domain_id` set, the company's role and welcome name (both follow the company's), every time on a new browser. Addresses on the list one by one open as before, and so does any listed address or company address for a signed-in admin, who never triggers an email. Links are limited per address and per company (`DOOR_LIMITS`); `{address}` in the door's sent message is the address typed (not `{email}`, which content fills with the contact address).

## Technical decisions (settled)

- Next.js App Router, TypeScript, Tailwind CSS v4, Motion (formerly Framer Motion).
- Postgres via Drizzle ORM (`pg` driver); migrations in `drizzle/`, generated with `npm run db:generate`. Never edit an applied migration; add a new one.
- The server applies migrations and seeds (admin account, settings, content) on startup, under an advisory lock. Nothing touches the database at build time. It applies them itself (`src/db/migrate.ts`), going by the hashes in the migrator's record rather than by date as Drizzle's own migrator does: every migration after the last one the record vouches for, and everything from the first migration whose tables or columns are missing against the newest snapshot, runs statement by statement, skipping what is already there. So a stray row in the record cannot make it skip everything, and a table that exists ahead of its migration cannot stop a start. Data migrations must therefore be safe to run twice: guard every change on the state it changes.
- Email through Resend from a dedicated operovia.com subdomain. Without `RESEND_API_KEY`, emails are printed to the server log.
- Uploads go through one storage adapter: local `uploads/` folder in development, S3-compatible bucket in production.
- Standard Node service (`npm run build`, `npm run start`). Nothing platform-specific.
- `src/instrumentation-client.ts` works around a bug in React's development build, in development only: its Server Component timings can end below zero, and the dev overlay then reports "'NotFound' cannot have a negative time stamp" (or another component's name) although the site is fine. Remove it once React fixes that upstream.
- Security: every admin page, action, and route calls `requireAdmin()`; mutations go through Server Actions (built-in origin check) or route handlers guarded by `isSameOrigin()` (`src/server/origin.ts`); parameterized queries only (Drizzle); secrets only in environment variables (documented in `.env.example`); honeypot plus rate limiting on public forms; tokens from at least 32 random bytes; audit log for publishes and logins.
- Public pages render on the server from an in-memory content cache that is checked against a content version number, so a publish shows up immediately on every server instance.
- Share previews use the image chosen in Settings, or else `/share-image.png`, drawn by the site from the hero headline (TTF copies of two Plus Jakarta Sans weights in `src/theme/fonts` exist only for this renderer). `sitemap.xml` and `robots.txt` are generated at request time from `SITE_URL`. Every absolute link comes from `siteUrl()` (`src/server/env.ts`): `SITE_URL` on the published app (`https://operovia.com`), but always the dev URL on Replit's development server, because Replit keeps one Secrets list for the workspace and the published app and the dev site's links must lead back to it.
- Surveys: once a survey has responses only wording may change (`structuralChange` in `src/surveys/questions.ts`); personal links submit once (the recipient row is locked); anonymous surveys never store who answered and keep only the day. Survey pages are noindex and deliberately not blocked in robots.txt, so crawlers can see the noindex.
